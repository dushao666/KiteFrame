# KiteServer 项目规范

> 本规范基于当前代码库（KiteServer / KiteFrame）的实际编码约定提炼而成，适用于本仓库所有 C# 代码的新增与修改。所有约定均以现有代码为准，新增代码请保持一致。

---

## 1. 技术栈与运行环境

| 类别 | 选型 |
| --- | --- |
| 运行时 | .NET 9（`net9.0`，见 `global.json`，SDK `9.0.0`） |
| 语言 | C#（启用 `Nullable` 与 `ImplicitUsings`） |
| ORM | SqlSugar（`SqlSugarCoreNoDrive`） |
| 数据库 | MySQL（默认），支持 PostgreSQL / SQLServer / SQLite / Oracle |
| 数据库迁移 | DbUp（`dbup-core` + `dbup-mysql`），Flyway 式 SQL 脚本 + 版本表，启动时自动执行 |
| 缓存 | Redis / 内存缓存（`ICacheService` 抽象） |
| 中介者 / CQRS | MediatR |
| 对象映射 | Mapster |
| 校验 | FluentValidation + DataAnnotations |
| 日志 | Serilog |
| 认证 | JWT Bearer |
| API 文档 | Swashbuckle + Knife4jUI / Scalar |
| 测试 | xUnit + coverlet（详见第 14 章） |

### 1.1 项目级编译约定（所有 `*.csproj` 统一）

```xml
<TargetFramework>net9.0</TargetFramework>
<ImplicitUsings>enable</ImplicitUsings>
<Nullable>enable</Nullable>
<GenerateDocumentationFile>True</GenerateDocumentationFile>
```

- 必须开启可空引用类型（`Nullable=enable`），并在代码中正确使用 `?`。
- 必须生成 XML 文档文件，Swagger 依赖其提供中文接口说明。

## 2. 解决方案与分层架构

采用**洋葱 / 整洁架构**，配合 **CQRS**（命令走 MediatR，查询走独立查询服务）。

```
src/
├── Api/            # Web API 层：Controllers、Extensions、Filters、Program.cs、appsettings
├── Application/    # 应用层：Commands、Handlers、Queries、Validators、DependencyInjection
├── Domain/         # 领域层：Entities、Entities/Base、Interfaces（最纯净，仅实体与契约）
├── Infrastructure/ # 基础设施：Exceptions、Extensions、Filters、Services、Utilities
├── Repository/     # 仓储：DBContext、Extensions（DI 装配 / 连接解析）、Migrations（迁移执行器）、Sql/Migrations（迁移脚本，按方言/年/月分子目录）
└── Shared/         # 共享：Attributes、Configuration、Constants、Enums、Events、Models
tests/
├── UnitTests/        # 单元测试：Validators、领域 / 纯逻辑（引用 Domain + Application + Repository）
└── IntegrationTests/ # 集成测试：HTTP 端点（引用 Api）
```

### 2.1 依赖方向（只能向下依赖，禁止反向）

```
Api ──> Application ──> Domain
 │          │             ▲
 │          └─> Repository ┘
 └─> Infrastructure ───────┘
所有层 ──> Shared（Shared 不依赖任何业务层）
```

- `Domain` 与 `Shared` 是最底层，不得引用其它业务项目。
- `Api` 负责组合根（依赖注入装配）与 HTTP 入口，不放业务逻辑。
- 业务逻辑写在 `Application` 的 Handler / Queries 中。

### 2.2 各层目录组织约定

- **按功能模块分子目录**，模块名与业务实体一致（`User`、`Role`、`Menu`、`Auth`、`Permission`、`Monitor`）。
  - `Application/Commands/{Module}/`、`Application/Handlers/{Module}/`
  - `Application/Queries/{Module}/` 及其 `Interfaces/` 子目录
  - `Shared/Models/{Module}/`
- 一个类型一个文件，文件名与类型名完全一致。
- 仓储层固定目录：
  - `Repository/Extensions/`：DI 装配与连接解析（`ServiceCollectionExtensions`、`DatabaseConnectionFactory`）。
  - `Repository/Migrations/`：数据库迁移执行器（`DatabaseMigrator`）与 DbUp 日志适配器。
  - `Repository/Sql/Migrations/{方言}/{年}/{月}/`：数据库迁移脚本（Flyway 风格 `V00xx__描述.sql`），按 方言 → 年 → 月 层级子目录存放（当前方言仅 `MySql/`），以 EmbeddedResource 嵌入 Repository 程序集。

## 3. 命名规范

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 实体 | 单数名词，继承 `BaseEntity` | `User`、`Role`、`Menu` |
| 命令 | `{动作}{模块}Command` | `CreateUserCommand`、`DeleteUserCommand` |
| 命令处理器 | `{命令名}Handler` | `CreateUserCommandHandler` |
| 查询服务 | `{模块}Queries` / 接口 `I{模块}Queries` | `UserQueries` / `IUserQueries` |
| 请求模型 | `{动作}{模块}Request` | `CreateUserRequest`、`GetUsersRequest` |
| 传输对象 | `{模块}Dto` | `UserDto`、`MenuDto` |
| 校验器 | `{命令名}Validator` | `SignInCommandValidator` |
| 配置类 | `{名称}Settings`，含 `const SectionName` | `JwtSettings` |
| 枚举 | 领域名词，成员显式赋值 | `Status`、`MenuType`、`DataScope` |
| 控制器 | `{模块}Controller` | `UserController` |
| 私有字段 | `_camelCase` | `_unitOfWork`、`_logger` |
| 属性 / 方法 | `PascalCase` | `UserName`、`GetUserByIdAsync` |
| 异步方法 | 以 `Async` 结尾 | `GetUsersAsync` |

- 命名空间与目录结构保持一致（如 `Application.Handlers.User`）。
- 使用**文件范围命名空间**：`namespace Application.Commands.User;`。

## 4. 通用编码风格

- 缩进使用 **4 个空格**，不使用 Tab。
- 优先使用 .NET 9 / 最新 C# 语法特性。
- 字符串属性默认值使用 `= string.Empty;`，而非 `null`（非可空字段）。
- 可空引用类型显式标注 `?`（如 `public string? Email { get; set; }`）。
- 依赖注入使用**显式构造函数注入**，字段声明为 `private readonly`。
- 集合属性初始化使用 `new()`（如 `public List<T> Items { get; set; } = new();`）。

### 4.1 全局 using（`_Imports.cs`）

每个项目根目录维护一个 `_Imports.cs`，集中管理 `global using`，并按类别用**中文注释分组**：

```csharp
// 全局导入文件 - Domain 项目

// .NET 基础命名空间
global using System;
global using System.Collections.Generic;
// ...

// SqlSugar ORM
global using SqlSugar;

// 项目特定命名空间
global using Shared.Configuration;
```

- 新增第三方或跨文件使用的命名空间，优先加入 `_Imports.cs`，避免在每个文件重复 `using`。
- 存在命名冲突时使用别名（见 `Api/_Imports.cs` 中的 `global using MenuDto = ...`）。

## 5. 注释与文档规范

- **所有公共类型与公共成员必须有 XML 文档注释**，且使用**中文**。
- 类使用 `<summary>`；方法使用 `<summary>` + `<param>` + `<returns>`。

```csharp
/// <summary>
/// 用户实体
/// </summary>
[SugarTable("sys_user", "用户表")]
public class User : BaseEntity
{
    /// <summary>
    /// 用户名
    /// </summary>
    [SugarColumn(ColumnDescription = "用户名", Length = 50, IsNullable = false)]
    public string UserName { get; set; } = string.Empty;
}
```

- 关键业务步骤使用行内中文注释说明意图（如 `// 检查用户名是否存在`、`// 加密密码`）。
- 枚举每个成员都要有 `<summary>`。

## 6. 领域层（Domain）规范

### 6.1 实体

- 所有实体继承 `BaseEntity`，自动获得审计字段（`Id`、`CreateTime`、`UpdateTime`、`CreateUserId`、`IsDeleted`、`DeleteTime` 等）。
- 使用 SqlSugar 特性标注表与列：
  - 类：`[SugarTable("sys_xxx", "中文表说明")]`，表名为小写 snake_case，系统表使用 `sys_` 前缀。
  - 列：`[SugarColumn(ColumnDescription = "中文说明", Length = n, IsNullable = ...)]`。
- 导航属性使用 `[SugarColumn(IsIgnore = true)]` 标注，不映射到数据库。

### 6.2 基础实体与软删除

- `BaseEntity` 实现 `IDeleted` 接口，提供 `IsDeleted` 软删除标记。
- 逻辑删除由 `Repository` 的 `DbSet<T>` 统一重写实现，业务代码**不要物理删除**。
- 审计字段（`CreateTime`/`UpdateTime`/`IsDeleted`）由 SqlSugar `Aop.DataExecuting` 自动填充，**业务代码不要手动赋值**。

## 7. 应用层（Application）规范 —— CQRS

### 7.1 命令（写操作）

- 命令实现 `IRequest<ApiResult<T>>`，返回统一结果。
- 命令为纯数据载体（属性 + 可选构造函数），不含逻辑。
- 简单命令可用构造函数传参（如 `DeleteUserCommand(long id)`）。

### 7.2 命令处理器（Handler）

- 实现 `IRequestHandler{TCommand, ApiResult<T>>`。
- 结构约定（务必遵循）：
  1. 构造函数注入 `ISugarUnitOfWork<DBContext>` 与 `ILogger<THandler>`。
  2. `Handle` 方法**整体包裹在 `try-catch` 中**。
  3. 使用 `using var context = _unitOfWork.CreateContext();` 开启工作单元。
  4. 业务校验失败：`return ApiResult<T>.Fail("中文错误信息");`。
  5. 对象转换使用 Mapster：`request.Adapt<Entity>()`。
  6. 成功后 `context.Commit();` 并记录日志，返回 `ApiResult<T>.Ok(data, "中文成功信息")`。
  7. `catch` 中 `_logger.LogError(ex, ...)` 并返回 `Fail`（不向外抛异常）。

```csharp
public async Task<ApiResult<long>> Handle(CreateUserCommand request, CancellationToken cancellationToken)
{
    try
    {
        using var context = _unitOfWork.CreateContext();
        // 业务校验...
        var user = request.Adapt<Domain.Entities.User>();
        var result = await context.Users.InsertReturnEntityAsync(user);
        context.Commit();
        _logger.LogInformation("创建用户成功，用户ID: {UserId}", result.Id);
        return ApiResult<long>.Ok(result.Id, "创建成功");
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "创建用户失败，用户名: {UserName}", request.UserName);
        return ApiResult<long>.Fail("创建用户失败");
    }
}
```

### 7.3 查询服务（读操作）

- 查询不走 MediatR，而是接口 + 实现的 Scoped 服务（`IUserQueries` / `UserQueries`）。
- 接口放在 `Queries/{Module}/Interfaces/` 目录。
- 使用 `_unitOfWork.CreateContext(false)`（只读上下文）。
- 同样使用 `try-catch` + `ApiResult` 包装，分页返回 `PagedResult<T>`。
- 查询服务由 `ApplicationServiceExtensions` **按约定自动注册**（类名以 `Queries` 结尾且存在同名 `I` 前缀接口）。

### 7.4 校验器（Validator）

- 使用 FluentValidation，继承 `AbstractValidator{TCommand}`。
- 校验消息使用中文；条件校验使用 `When(...)`。
- 请求模型（Request）可同时使用 DataAnnotations（`[Required]`、`[StringLength]`，`ErrorMessage` 为中文）。

## 8. API 层（Api）规范

### 8.1 控制器

- 继承 `ControllerBase`，标注 `[ApiController]` 与 `[Route("api/[controller]")]`。
- 构造函数注入 `IMediator`（发命令）、查询接口、`ILogger`。
- 每个 Action 必须：
  - 标注 HTTP 动词特性（`[HttpGet]`/`[HttpPost]`/`[HttpPut]`/`[HttpDelete]`）。
  - 标注 `[ProducesResponseType(typeof(ApiResult<...>), StatusCodes.Status...)]` 声明可能的响应。
  - 使用参数绑定特性：`[FromQuery]`、`[FromBody]`、路径参数直接命名。
- **写操作**：将 Request 映射为 Command，`await _mediator.Send(command)`。
- **读操作**：直接调用查询服务。
- **统一返回**：`return Ok(result);`（result 为 `ApiResult`），不要直接返回裸数据。

```csharp
[HttpPost]
[ProducesResponseType(typeof(ApiResult<long>), StatusCodes.Status200OK)]
[ProducesResponseType(typeof(ApiResult), StatusCodes.Status400BadRequest)]
public async Task<IActionResult> CreateUser([FromBody] CreateUserRequest request)
{
    var command = new CreateUserCommand { UserName = request.UserName, /* ... */ };
    var result = await _mediator.Send(command);
    return Ok(result);
}
```

### 8.2 程序入口（Program.cs）

- 使用扩展方法组织启动逻辑（`ConfigureSerilog`、`ConfigureServices`、`ConfigurePipeline`、`RunWithExceptionHandlingAsync`）。
- 顶层用 `try-catch-finally` 包裹，`Log.Fatal` 记录启动失败，`finally` 中 `Log.CloseAndFlush()`。

---

## 9. 共享层（Shared）规范

### 9.1 统一返回结果

- 所有对外接口返回 `ApiResult<T>` / `ApiResult`。
- 使用静态工厂 `ApiResult<T>.Ok(data, message)` 与 `ApiResult<T>.Fail(message, code)`。
- 成功码 `200`，失败默认码 `400`。

### 9.2 分页模型

- 请求继承 `BasePageRequest`（`PageIndex` 默认 1，`PageSize` 默认 10）。
- 响应使用 `PagedResult<T>`（含 `Items`、`TotalCount`、`TotalPages`、`HasPreviousPage`、`HasNextPage`）。

### 9.3 配置类

- 放在 `Shared/Configuration/`，命名 `{名称}Settings`。
- 提供 `public const string SectionName`，供 `configuration.GetSection(...)` 绑定。
- 所有属性提供合理默认值。

### 9.4 枚举

- 放在 `Shared/Enums/`，成员显式赋整数值，每个成员带中文 `<summary>`。

## 10. 仓储层（Repository）规范

- `DBContext` 继承 `SugarUnitOfWork`，用 `DbSet<T>` / `SimpleClient<T>` 暴露实体集合，属性初始化为 `null!`。
- 需要软删除的集合用 `DbSet<T>`（重写删除为逻辑删除）；关联表可用 `SimpleClient<T>`。
- 数据库装配在 `ServiceCollectionExtensions.AddCustomDatabase` 中完成：
  - 依据配置选择 `DbType` 与连接字符串。
  - 注册全局查询过滤器 `AddTableFilter<IDeleted>(x => x.IsDeleted == false)`。
  - 通过 `Aop.DataExecuting` 自动填充审计字段。
  - `ISugarUnitOfWork<DBContext>` 以单例注册。
- 数据库连接解析统一由 `DatabaseConnectionFactory.Resolve(IConfiguration)` 完成（返回配置的数据库类型、SqlSugar `DbType`、连接字符串），`AddCustomDatabase` 与迁移执行器共用；**禁止在其他位置重复实现类型映射与连接串回退逻辑**。

### 10.1 数据库迁移（DbUp）

表结构变更一律通过迁移脚本落地，不允许手工改库。

- 脚本位置：`src/Repository/Sql/Migrations/{方言}/{年}/{月}/`，方言子目录与 `DatabaseType` 一一对应（`MySql` / `PostgreSQL` / `SQLServer` / `SQLite` / `Oracle`），方言之下再按脚本创建日期的年（4 位）/ 月（2 位）分子目录；随 Repository 程序集嵌入发布；仓库当前仅维护 `MySql/` 一套。
- 命名：Flyway 风格 `V00xx__描述.sql`——四位零填充编号 + 双下划线 + 小写字母 / 数字 / 下划线描述（如 `MySql/2026/07/V0001__init_rbac_schema.sql`）；DbUp 按嵌入资源名顺序执行（年月目录排在文件名之前），因此**年月目录顺序必须与版本号顺序一致**——编号更大的脚本必须放在相同或更晚的年月目录。版本号在**同一方言内唯一**，不同方言可以各自从 V0001 起编。
- 版本表：`sys_schema_versions`（DbUp 自动创建，记录已执行脚本名与应用时间；遵循 `sys_` 系统表前缀约定）。版本表建在每个数据库实例内，因此切换到新数据库时，对应方言目录下的全部脚本会自动重新执行。
- 执行时机：应用启动时（`ConfigurePipeline` 最前端），迁移器按当前 `DatabaseType` 的方言目录前缀过滤嵌入脚本，自动执行该目录下所有未执行的脚本。尚未接入迁移引擎的数据库类型（当前为 MySQL 以外的全部类型）记录警告并跳过，不阻断启动；已支持数据库下迁移失败视为启动失败（快速失败）。
- 幂等要求（脚本可能被重跑，必须安全）：
  - 建表使用 `CREATE TABLE IF NOT EXISTS`；
  - 初始化数据使用 `INSERT IGNORE`；
  - 禁止出现 `DROP TABLE` / `CREATE DATABASE` / `USE`（建库由 `EnsureDatabase` 自动完成）。
- **已执行的脚本禁止修改**（版本表按脚本名记录，修改不会触发重跑）；任何变更新增下一个编号的脚本。
- 新增迁移流程：在对应方言目录（当前为 `Sql/Migrations/MySql/`）下的当前年/月目录（不存在则新建）新建 `V00xx__描述.sql` → `dotnet build` → 启动应用观察迁移日志 → 确认 `sys_schema_versions` 新增对应记录。

## 11. 依赖注入规范

- 每层提供 `Add{Layer}Services` 静态扩展方法（位于 `DependencyInjection/` 或 `Extensions/`）。
- 查询服务按约定自动扫描注册；命令处理器由 MediatR 自动发现。
- 映射集中在 `MapsterConfiguration : IRegister`，通过 `TypeAdapterConfig.GlobalSettings.Scan(...)` 加载。
- 新增服务优先复用现有扩展方法入口，保持 `Program.cs` 简洁。

---

## 12. 日志规范

- 通过构造函数注入 `ILogger<T>`（T 为当前类）。
- 使用**结构化日志**（占位符 `{Name}`），不要字符串拼接。
- 操作成功用 `LogInformation`，异常用 `LogError(ex, ...)`，消息使用中文并携带关键业务参数。
- 可复用 `Infrastructure` 中的日志扩展方法（操作日志、安全日志、性能日志等）。

---

## 13. 异常处理规范

- Handler / Query 内部捕获异常并转为 `ApiResult.Fail`，**不向控制器抛出业务异常**。
- 可预期的友好错误使用 `FriendlyException`（`Infrastructure/Exceptions`）。
- 启动阶段异常在 `Program.cs` 顶层捕获并 `Log.Fatal`。

---

## 14. 测试规范

测试分 `tests/UnitTests` 与 `tests/IntegrationTests` 两个项目，统一使用 **xUnit**，不使用 NUnit / MSTest。

### 14.1 技术选型与项目划分

| 测试项目 | 引用项目 | 适用范围 |
| --- | --- | --- |
| `tests/UnitTests` | `Domain`、`Application`、`Repository` | 校验器（Validator）、领域 / 纯逻辑、工具类、映射配置、迁移脚本命名守护 |
| `tests/IntegrationTests` | `Api` | HTTP 端点的端到端验证（`WebApplicationFactory<Program>`） |

- 包统一为 `xunit`（当前 `2.9.2`）+ `Microsoft.NET.Test.Sdk` + `coverlet.collector`（覆盖率收集）；仓库未启用集中包版本管理，**两个测试项目的版本号必须保持一致**，升级时同步修改。
- 测试项目已在 csproj 通过 `<Using Include="Xunit" />` 全局引入，测试代码无需写 `using Xunit;`；其它需共享的命名空间优先在 csproj 追加 `<Using>`。
- **尚未引入 Mock 库**：单元测试需要模拟依赖时，推荐引入 NSubstitute，并在两个测试项目中统一版本。
- 分层定位：Handler / Queries 依赖 `ISugarUnitOfWork<DBContext>` 与真实数据库行为，**以集成测试覆盖为主**；单元测试聚焦校验器、领域逻辑与可独立测试的纯逻辑。

### 14.2 目录组织与命名

- 测试目录**镜像 src 的分层 / 模块结构**：`UnitTests/Validators/{Module}/`、`UnitTests/Handlers/{Module}/`、`UnitTests/Domain/` 等。
- 测试类命名 `{被测类型}Tests`，一个类型一个文件，文件名与类型名完全一致（如 `SignInCommandValidatorTests.cs`）；文件范围命名空间与目录一致（如 `namespace UnitTests.Validators.Auth;`）。
- 测试方法命名 `{被测方法}_{场景}_{预期}`，如 `ValidateAsync_PasswordLoginWithEmptyUserName_Fails`。
- `[Fact]` / `[Theory]` 统一通过 `DisplayName` 给出**中文描述**，与项目中文文档风格保持一致。

### 14.3 单元测试编写约定

- 遵循 Arrange-Act-Assert 结构，使用中文行注释分隔三段：`// 准备` / `// 执行` / `// 断言`。
- 一个测试方法只验证一个行为；参数化场景使用 `[Theory]` + `[InlineData]`。
- 断言统一使用 xUnit 的 `Assert.*`；异常断言使用 `Assert.ThrowsAsync<T>`；`ApiResult` 类结果断言其 `Success` / `Code` / `Message`。
- 测试数据在各方法内就地准备（Arrange），避免共享可变字段（xUnit 为每个测试方法创建测试类新实例；确需共享夹具时使用 `IClassFixture<T>`）。
- 代码风格与 src 一致：4 空格缩进、文件范围命名空间、公共测试类写中文 `<summary>`。

```csharp
using Application.Commands.Auth;
using Application.Validators.Auth;
using FluentValidation;
using Shared.Enums;

namespace UnitTests.Validators.Auth;

/// <summary>
/// <see cref="SignInCommandValidator"/> 单元测试
/// </summary>
public class SignInCommandValidatorTests
{
    [Fact(DisplayName = "账号密码登录：用户名为空时校验应失败")]
    public async Task ValidateAsync_PasswordLoginWithEmptyUserName_Fails()
    {
        // 准备
        var validator = new SignInCommandValidator();
        var command = new SignInCommand
        {
            Type = LoginType.Password,
            UserName = string.Empty,
            Password = "123456"
        };

        // 执行
        var result = await validator.ValidateAsync(command);

        // 断言
        Assert.False(result.IsValid);
        Assert.Contains(result.Errors, e => e.PropertyName == nameof(SignInCommand.UserName));
    }

    [Theory(DisplayName = "手机验证码登录：手机号格式校验")]
    [InlineData("13800138000", true)]
    [InlineData("12345", false)]
    public async Task ValidateAsync_SmsCodeLoginPhoneFormat_ChecksRegex(string phone, bool expected)
    {
        // 准备
        var validator = new SignInCommandValidator();
        var command = new SignInCommand
        {
            Type = LoginType.SmsCode,
            Phone = phone,
            SmsCode = "123456"
        };

        // 执行
        var result = await validator.ValidateAsync(command);

        // 断言
        Assert.Equal(expected, result.IsValid);
    }
}
```

### 14.4 集成测试约定

- `IntegrationTests` 目前仅有脚手架代码；正式编写集成测试前，先在该项目补充 `Microsoft.AspNetCore.Mvc.Testing` 包（与 `Microsoft.NET.Test.Sdk` 同为 .NET 9 版本线）。

/// <summary>

## 15. 新增功能的标准流程（Checklist）

以新增「用户管理」类功能为例，按下列顺序创建文件：

1. **Domain**：实体 `Xxx`（继承 `BaseEntity`，加 `[SugarTable]`/`[SugarColumn]`），并在 `DBContext` 暴露 `DbSet<Xxx>`。
2. **迁移脚本**：若涉及表结构变更（新增表 / 新增列等），在 `Repository/Sql/Migrations/` 对应方言目录（当前为 `MySql/`）下的当前年/月目录新增 `V00xx__描述.sql`（幂等写法见 10.1）；实体 `[SugarTable]` 表名必须与脚本一致。
3. **Shared/Models**：`XxxDto`、`CreateXxxRequest`、`UpdateXxxRequest`、`GetXxxRequest`（分页继承 `BasePageRequest`）。
4. **Application/Commands**：`CreateXxxCommand` / `UpdateXxxCommand` / `DeleteXxxCommand`（`IRequest<ApiResult<T>>`）。
5. **Application/Handlers**：对应 Handler（`try-catch` + 工作单元 + Mapster + `ApiResult`）。
6. **Application/Queries**：`IXxxQueries`（含 `Interfaces/`）+ `XxxQueries`（只读上下文）。
7. **Application/Validators**：`XxxCommandValidator`（FluentValidation，中文消息）。
8. **MapsterConfiguration**：补充 `Entity <-> Dto`、`Command -> Entity` 映射。
9. **Api/Controllers**：`XxxController`（`[ApiController]` + `ProducesResponseType` + `Ok(result)`）。
10. **Tests**：在 `tests/UnitTests` 为新 Validator、纯逻辑补测试；重要端点在 `tests/IntegrationTests` 补集成测试（见第 14 章），并确保 `dotnet test` 通过。

## 17. 专项技术用法速记

> 本章汇总依赖注入配置、Mapster 对象映射、事件驱动系统监控模块三个专项的用法要点（原为独立指南文档，已合并至此）；细节实现以对应代码为准。

### 17.1 依赖注入配置

- 应用层服务统一经 `Application/DependencyInjection/ApplicationServiceExtensions.AddApplicationServices()` 入口注册，**禁止在 `Program.cs` / `ProgramExtensions.cs` 中逐个零散注册**。
- 查询服务按命名约定自动扫描注册，无需手动注册：
  - 约定：接口 `I{模块}Queries` + 实现类 `{模块}Queries`（如 `IUserQueries` / `UserQueries`），自动注册为 `Scoped` 生命周期；
  - 新增查询服务只需创建接口与实现类（构造函数注入 `ISugarUnitOfWork<DBContext>` 与 `ILogger<T>`），即自动被发现。
- 命令处理器与事件处理器由 MediatR 自动发现；Mapster 配置经扫描 `MapsterConfiguration : IRegister` 加载（见第 11 章）。

### 17.2 Mapster 对象映射

- 映射规则统一集中在 `Application/DependencyInjection/MapsterConfiguration.cs`（`IRegister`），用 `config.ForType<TSource, TDest>()` 声明，由 `TypeAdapterConfig.GlobalSettings.Scan(...)` 加载。
- 常用用法：

```csharp
var dto = entity.Adapt<UserDto>();          // 单对象映射
var dtos = entities.Adapt<List<UserDto>>(); // 集合映射
var user = command.Adapt<User>();           // Command → 实体
```

- 字段定制：`.Map(dest => dest.X, src => ...)` 自定义表达式；`.Ignore(dest => dest.Password)` 忽略敏感字段。
- 约定：密码等敏感字段必须忽略；禁止在循环中重复配置映射；复杂映射添加注释说明。

### 17.3 事件驱动系统监控模块

- 架构：以 MediatR 作为事件总线，业务操作发布事件、处理器异步记录监控数据，实现业务与监控解耦；监控异常不得影响主业务流程。
- 事件定义在 `Shared/Events`（实现 `INotification`），处理器实现 `INotificationHandler<T>`，由 MediatR 自动发现：
  - `UserLoginEvent` / `UserLogoutEvent`：登录 / 退出时发布，处理器维护在线用户 `OnlineUser`（会话 ID 即 RefreshToken）与登录日志 `LoginLog`；
  - `OperationLogEvent`：操作日志记录。
- 操作日志声明式用法：在控制器或 Action 上标记 `[OperationLog(Module = "...", BusinessType = "...", Title = "...")]`，全局注册的 `OperationLogFilter` 自动拦截并记录到 `OperationLog` 表；`Exclude = true` 排除记录，`IsSaveRequestData` / `IsSaveResponseData` 控制是否保存请求 / 响应数据。
- 监控查询端点：`GET /api/monitor/online-users`、`/api/monitor/login-logs`、`/api/monitor/operation-logs`。
- 新增监控事件步骤：`Shared/Events` 创建事件类 → 创建对应处理器 → 业务点 `await _mediator.Publish(...)` 发布。
- 注意事项：事件处理为异步（允许短暂数据不一致）；处理器必须幂等并自行捕获异常记录日志；监控表数据持续增长，需建立索引并定期清理。

## 附：核心约定速记

- **分层**：Api → Application → Domain / Repository / Infrastructure，Shared 全局共享。
- **CQRS**：写走 MediatR Command+Handler，读走 `IxxxQueries`。
- **返回**：一律 `ApiResult<T>`，控制器 `Ok(result)`。
- **删除**：一律逻辑删除（`IDeleted` + 查询过滤器）。
- **审计**：`CreateTime`/`UpdateTime`/`IsDeleted` 由 AOP 自动维护。
- **映射**：统一 Mapster，集中在 `MapsterConfiguration`。
- **注释**：公共成员全量中文 XML 注释。
- **风格**：4 空格缩进、文件范围命名空间、`_Imports.cs` 集中 using、`string.Empty` 默认值、可空引用类型。
- **测试**：统一 xUnit，目录命名镜像 src；新功能必须同步补测试，提交前 `dotnet test` 全通过。
- **迁移**：DbUp 嵌入式脚本（`Repository/Sql/Migrations/{方言}/{年}/{月}/V00xx__*.sql`）启动时按当前数据库方言过滤后自动执行，版本表 `sys_schema_versions`；结构变更只允许新增脚本，禁止改旧脚本、禁止手工改库。
